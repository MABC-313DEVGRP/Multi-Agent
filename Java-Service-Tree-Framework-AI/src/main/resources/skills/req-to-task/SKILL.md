# 요구사항 착수 변환기

## 1. 이 스킬이 푸는 문제

SI·SW 프로젝트에서 요구사항정의서는 엑셀로 관리된다. 그런데 엑셀 한 행은 개발자가 바로 착수할 수 있는 형태가 아니다.

- `요구사항명`은 **명사구**다 — "다중 클러스터 설정 정보 수집". 무엇이 되어 있으면 끝인지 없다.
- `상세 내용`은 한 셀에 개요·기능·제약·검증이 뭉쳐 있다. 셀이 잘려 화면에서 안 보이기도 한다.
- **완료 조건이 없거나, 있어도 "안정적으로 동작할 것" 같은 판정 불가능한 문장이다.**

그래서 PM·PL이 매 건 이걸 읽고 해석해 작업 지시로 옮긴다. **프로젝트 착수 시 50~200건, 건당 10~15분.** 요구사항이 변경될 때마다 반복된다.

더 큰 비용은 시간이 아니라 **해석 편차**다. 옮기는 사람마다 "완료"의 기준이 달라져서, 검수 단계에서 "이거 다 된 거 맞나요?"가 터진다. 이때는 이미 되돌릴 수 없다.

**이 스킬은 그 해석을 고정된 규칙으로 대신하고, 규칙으로도 메울 수 없는 빈칸을 착수 전에 드러낸다.**

## 2. 설계 원칙 — 지어내지 않는다

일반적인 변환 도구는 입력을 그럴듯한 출력으로 바꾼다. 정보가 없으면 **채워 넣는다.** 이게 가장 위험하다. 없는 완료 조건을 그럴듯하게 지어내면, 그 문장이 나중에 검수 기준이 되어 버린다.

이 스킬은 반대로 동작한다.

| 상황 | 하지 않는 것 | 하는 것 |
|---|---|---|
| 완료 조건이 없다 | 그럴듯하게 생성 | `❓확인 필요`로 표시하고 질문 |
| 완료 조건이 모호하다 | 그대로 옮김 | 측정 가능한 문장으로 바꿀 안을 제시하고 확인 요청 |
| 원문에 없는 기술 스택·수치 | 상식으로 보충 | 쓰지 않음 |
| 요구사항 2건이 한 행에 섞임 | 하나로 뭉갬 | 분할을 제안 |

**추론한 것은 반드시 추론이라고 표시한다.** 원문에 있는 것과 스킬이 판단한 것이 출력에서 구분되지 않으면 이 스킬은 실패한 것이다.

## 3. 입력 받기

다음을 전부 받는다. 어떤 형태든 먼저 **필드 역할부터 인식**한다.

- 엑셀 행 복사·붙여넣기 (탭 구분)
- CSV / 마크다운 표
- `요구사항명: ... / 상세: ...` 형태의 평문
- 요구사항 문장 한 줄 (컬럼 없음)
- 여러 건 동시

입력이 없이 스킬만 호출되면 이렇게 답한다:

> 요구사항정의서 행이나 요구사항 문장을 붙여넣어 주세요.
> 엑셀 행 복붙, CSV, 그냥 문장 모두 됩니다. **엑셀 파일을 그대로 주셔도 됩니다.**

**파일도 받는다.** 붙여넣기가 유일한 입구가 아니다.

- 워크스페이스에 파일이 있으면 `ls`·`find`로 찾고 `read`로 읽는다
- `.xlsx`는 `bash`로 파싱한다 (python). 헤더 행을 찾아 STEP 1의 역할 인식을 그대로 적용한다
- 시트가 여러 개면 요구사항 데이터가 있는 시트를 고르고, **어느 시트를 썼는지 밝힌다**
- 파싱에 실패하면 붙여넣기를 요청한다. 추측해서 읽지 않는다

### 입력이 없을 때 — 즉시 시연 경로

안내만 하고 끝내지 않는다. **바로 보여줄 수 있는 길을 함께 제시한다.**

> 붙여넣을 자료가 마땅치 않으시면 **"샘플로 보여줘"** 라고 해주세요.
> 예시 데이터로 바로 시연해 드립니다.

"샘플로 보여줘" 요청을 받으면 **§7 예시의 입력 데이터를 그대로 써서** 전 과정을
수행하고 결과를 낸다. 새로 만들어내지 않는다.

시연을 마치면 반드시 이렇게 닫는다:

> 이건 예시 데이터입니다. **실제 자료를 넣어 보세요** — 형식이 달라도 됩니다.

시연으로 끝내면 안 된다. 이 스킬의 값어치는 사용자의 실제 자료에서 나온다.

## 4. 처리 절차

### STEP 1 — 필드 역할 인식 (양식 비종속)

컬럼명은 조직마다 다르다. **이름이 아니라 역할로 매칭한다.**

| 역할 | 실제로 쓰이는 컬럼명 |
|---|---|
| 식별자 | 요구사항 ID, ID, No, 번호, 항목번호 |
| 분류 | 대/중/소분류, 구분, 모듈, 기능분류, 카테고리 |
| 이름 | 요구사항명, 기능명, 제목, 요구사항 |
| 내용 | 상세 내용, 상세, 설명, 내용, 요구사항 상세 |
| 채택 | 수용 여부, 채택, 반영 여부, 검토 결과 |
| 중요도 | 우선순위, 중요도, 등급, Priority |
| 상태 | 진행 현황, 상태, 진행 상태, Status |
| 담당 | 담당자, 담당, 개발자, Assignee |
| 요청 | 요청자, 요청 부서, 고객 |
| 기타 | 비고, 특이사항, Remark |

`상세 내용` 안의 블록도 이름이 제각각이다. 역할로 매칭한다.

| 역할 | 실제 블록명 |
|---|---|
| 배경 | `[개요]` `[배경]` `[목적]` |
| 작업 범위 | `[상세 기능 요구사항]` `[기능]` `[요구사항 상세]` `[입력/출력]` `[I/O]` |
| 제약 | `[제약 조건]` `[제약사항]` `[비기능 요구사항]` |
| 완료 조건 | `[검증 기준]` `[인수 조건]` `[완료 조건]` `[테스트 기준]` |

> 같은 조직 안에서도 작성 가이드와 실제 셀의 블록명이 어긋나는 경우가 흔하다. 이름으로 매칭하면 거기서 깨진다.

**블록이 아예 없는 한 문단 서술이면** 문장 단위로 역할을 추정한다. 금지·불가·말 것 → 제약. ~되어야 한다·~확인된다 → 완료 조건. 나머지 → 작업 범위. 추정한 항목은 전부 `(추정)`을 붙인다.

### STEP 2 — 변환 규칙

**제목** — 명사구 40자 이내. 원문이 동사형·문장형이면 명사구로 정규화한다.

**배경** — 왜 필요한지 1~2문장. 원문에 없으면 비운다. 만들지 않는다.

**작업 범위** — 해야 할 일을 체크 가능한 단위로 쪼갠다. 원문 기능 항목을 그대로 옮기되, 하나의 항목에 동작이 2개 이상 섞여 있으면 나눈다.

**완료 조건** — 이 스킬의 핵심 산출물.

- 원문의 검증·인수 기준을 **판정 가능한 문장**으로 옮긴다.
- 각 항목에 판정 결과를 붙인다: `✅` 측정 가능 / `⚠️` 모호
- `⚠️`에는 반드시 **측정 가능하게 바꾼 대안 문장**과 확인 질문을 같이 낸다.

모호 표현은 아래 사전으로 판정한다.

| 모호 표현 | 되물을 것 |
|---|---|
| 빠르게, 신속히 | 몇 초·몇 ms 이내인가 |
| 안정적으로, 문제없이 | 허용 실패율·가동률이 얼마인가 |
| 편리하게, 직관적으로 | 어떤 동작이 몇 단계로 끝나야 하는가 |
| 실시간으로 | 허용 지연이 얼마인가 |
| 대량의, 다수의 | 몇 건인가 |
| 적절히, 유연하게 | 판단 기준이 무엇인가 |
| 최적화, 개선 | 현재 값과 목표 값이 얼마인가 |
| 사용자 친화적 | 어떤 지표로 측정하는가 |
| ~등, 기타 | 목록을 닫을 수 있는가 |

**제약** — **금지 항목만 남긴다.**

원문의 제약 블록에는 금지("쓰기 작업 금지")와 준수("TLS 적용", "페이징 처리")가 섞여 있다. 준수 항목을 제약에 두면 금지문 사이에 섞여 무시된다. 그래서 분리한다.

- 금지·하지 말 것 → **제약**
- 달성해야 할 품질 → **완료 조건**으로 올림
- 이미 정해진 환경 → **전제**

**전제** — 이미 확정되어 논의 대상이 아닌 환경.

**산출물** — 상태 필드에서 유도한다. 원문에 상태가 없으면 비우고 확인 질문으로 돌린다.

| 상태 | 산출물 |
|---|---|
| 기획중 · 분석중 | 분석·설계 문서 |
| 설계중 | 상세 설계·스키마 |
| 개발중 | 소스 코드 |
| 테스트중 · 검증중 | 테스트 케이스·결과 |

**우선순위 · 분류** — 원문에 있으면 그대로 옮긴다. 척도가 조직마다 달라도(`High/Medium/Low`, `상/중/하`, `1/2/3`) 원문 표기를 유지한다. **임의로 환산하지 않는다.** 원문에 없으면 이 줄을 통째로 생략한다.

**개인정보 제거** — 담당자·요청자 필드의 실명은 **역할로 치환하고 이름은 출력하지 않는다.**
`DEV: 홍길동 / SE: 김철수` → `개발 담당, 시스템 담당`
작업 지시서에 필요한 것은 역할이지 이름이 아니다. 이름을 남기면 문서가 유출됐을 때 그대로 개인정보가 된다.

### STEP 3 — 결손 진단

변환 후, 착수를 막는 빈칸을 찾아 표시한다. 없으면 "결손 없음"이라고 명시한다.

| 표시 | 의미 |
|---|---|
| `❓` | 정보가 없다. 지어내지 않고 물어본다 |
| `⚠️` | 있지만 판정 불가능하다. 대안 문장을 제시한다 |
| `🔀` | 한 건에 요구사항이 2개 이상 섞였다. 분할을 제안한다 |
| `🚫` | 변환하면 안 되는 행이다 (미수용·보류 등) |
| `📌` | 스킬이 원문을 손댄 곳이다 (실명 제거, 제약→완료 조건 이동 등). 사용자가 되돌릴 수 있도록 반드시 남긴다 |

### STEP 4 — 출력 전 자가 점검

아래를 통과하지 못하면 출력하지 않고 고친다.

- [ ] 완료 조건이 전부 `✅` 또는 `⚠️`로 판정되었는가
- [ ] `제약`에 긍정문(해야 할 일)이 섞이지 않았는가
- [ ] **원문에 없는 사실·수치·기술명을 추가하지 않았는가**
- [ ] 추론한 항목에 `(추정)`이 붙어 있는가
- [ ] 실명이 남아 있지 않은가
- [ ] 제목이 명사구인가
- [ ] 파일을 만들었다면 `share_file`로 공유했는가

### STEP 5 — 산출물 생성·공유

1. **변환 결과와 결손 진단을 대화창에 낸다.** 이건 항상 한다.
2. 건수가 많거나 사용자가 파일을 원하면 `write`로 만들고 `share_file`로 내려받게 한다.
3. **되돌리기 형식** — "엑셀로" 요청 시 원본 요구사항정의서 컬럼 구성으로 되돌려 준다.
   `bash`로 `.xlsx` 시도 → 실패 시 `.csv`(**UTF-8 BOM**) → `share_file`.
   BOM이 없으면 엑셀에서 한글이 깨진다.

파일명은 영문·숫자로 짓는다 — `requirements_tasks.csv`.

> **파일을 못 만들어도 변환 결과는 반드시 낸다.** 파일 생성 실패로 산출물이 통째로 없어지면 안 된다.

### STEP 6 — 확인 질문 (`ask_user_form`)

결손 진단에서 나온 `❓`·`⚠️`를 **한 폼으로 묶어** 물어본다.

**순서를 지킨다 — 변환 결과를 먼저 내고, 그다음에 묻는다.** 질문 때문에 산출물을 미루지 않는다.

- 질문은 **최대 3개**. 많으면 답하지 않는다
- `⚠️`(모호한 완료 조건)는 **제시한 대안 문장을 선택지로** 만든다. 사용자는 고르기만 하면 된다
- 각 질문에 `모르겠다 / 나중에 정하겠다`와 `직접 쓰겠다` 선택지를 **반드시** 넣는다
- 답이 오면 완료 조건을 갱신해 다시 내고, 파일도 다시 공유한다
- 답이 없으면 이미 낸 것이 최종본이다. 해당 항목은 `❓`로 남긴다

착수를 막는 것부터 묻는다. `🔀`(요구사항 2건 혼재)와 완료 조건 결손이 우선이다.

## 5. 출력 형식

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
[요구사항 ID] 제목
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

■ 배경
  (1~2문장. 없으면 "원문에 없음")

■ 작업 범위
  1) ...
  2) ...

■ 완료 조건
  ✅ (측정 가능한 판정 기준)
  ⚠️ (모호) "원문 표현"
     → 대안: (측정 가능하게 고친 문장)

■ 제약 (하지 말 것)
  - ...

■ 전제
  - ...

■ 산출물
  ...

■ 우선순위 / 분류
  (원문에 있을 때만. 없으면 줄 자체를 생략)

━━━ 결손 진단 ━━━
❓ ...
⚠️ ...
🔀 ...
```

여러 건을 처리하면 각 건을 위 형식으로 출력한 뒤, 마지막에 요약한다.

```
━━━ 요약 (총 N건) ━━━
착수 가능       : N건
확인 필요       : N건 → [ID 목록]
분할 권장       : N건 → [ID 목록]
변환 제외       : N건 → [ID 목록]
```

## 6. 예외 처리

| 입력 상황 | 처리 |
|---|---|
| 완료 조건 블록이 없다 | 지어내지 않는다. `❓완료 조건 없음 — 이 요구사항이 끝났다고 판단할 기준은 무엇입니까?` |
| 완료 조건이 모호하다 | `⚠️` + 모호 표현 사전으로 대안 제시 |
| 상세 내용이 블록 없는 한 문단 | 문장 단위 역할 추정, 전부 `(추정)` 표시 |
| 컬럼명이 표에 없는 이름 | 내용을 보고 역할 추정. 판단 불가면 `❓` |
| 컬럼 헤더 없이 값만 붙여넣음 | 값의 형태로 추정 (`REQ-`로 시작→ID, `High/Medium/Low`→중요도). 애매하면 되물음 |
| 한 행에 요구사항 2건 이상 | `🔀` 분할 제안 + 분할안 제시. 원본도 함께 변환해 둔다 |
| 채택 필드가 미수용·보류·검토중 | `🚫` 변환하지 않는다. `채택 상태가 '보류'입니다. 확정 후 진행하십시오.` |
| 상태 필드가 완료·취소 | 변환하되 `이미 완료/취소된 건입니다` 경고를 먼저 낸다 |
| 요구사항명만 있고 상세가 비었다 | 제목만 변환. 나머지는 전부 `❓` |
| 상세만 있고 이름이 없다 | 내용에서 명사구 제목을 만들고 `(추정)` 표시 |
| **엑셀 복붙 시 한 행이 여러 줄로 쪼개짐** (셀 안 Alt+Enter 줄바꿈 때문) | 줄 수로 행을 세지 않는다. **식별자 패턴(`REQ-`, 연번)이 줄 맨 앞에 나오는 지점**을 행 경계로 삼고, 그 사이 줄은 직전 행의 이어지는 내용으로 붙인다. 식별자가 없으면 `[개요]` 등 블록 머리표가 다시 나오는 지점을 경계로 본다 |
| 행 경계를 판정할 수 없다 | 추측해서 쪼개지 않는다. 인식한 건수를 먼저 알리고 `N건으로 보입니다. 맞습니까?` 확인 후 진행 |
| 셀이 중간에 잘려 문장이 끊김 | `❓ 내용이 중간에 끊겼습니다. 잘린 부분을 확인해 주세요.` 끊긴 부분은 변환하지 않는다 |
| 6건 이상 붙여넣음 | 먼저 목록과 건수를 요약해 보여주고, 전체 변환할지 특정 건만 할지 확인 |
| 빈 행·머리글만 | 데이터 행이 없다고 알린다 |
| 요구사항이 아닌 입력 (잡담·코드 등) | 스킬 범위를 한 줄로 안내하고 올바른 입력 형태를 제시 |
| 한국어가 아닌 요구사항 | 원문 언어를 유지해 변환한다 |
| 담당자·요청자에 실명 | 역할로 치환, 이름 미출력 |
| **파일 생성·공유에 실패했다** | 변환 결과를 대화창에 그대로 낸다. 파일을 못 만든 사실을 알린다. **산출물 없이 끝내지 않는다** |
| `.xlsx` 생성 라이브러리가 없다 | `.csv`(UTF-8 BOM)로 폴백하고 한 줄로 알린다. 오류 메시지를 그대로 보여주지 않는다 |
| 엑셀 파일을 첨부로 받았다 | `read`·`bash`로 파싱. 시트가 여럿이면 어느 시트를 썼는지 밝힌다 |
| 파싱에 실패했다 | 추측하지 않는다. 해당 행을 붙여넣어 달라고 요청 |
| 사용자가 확인 질문에 답하지 않았다 | 이미 낸 산출물이 최종본이다. 미답 항목은 `❓`로 남긴다 |
| 결손이 하나도 없다 | `결손 없음 — 이대로 착수 가능합니다`를 명시 (비워두지 않는다) |

## 7. 예시

**입력** (엑셀 행 복붙, 탭 구분)

```
REQ-F-014	주문	결제	취소	주문 취소 처리	[개요]
결제 완료된 주문에 대해 사용자가 취소를 요청하면 결제 취소와 재고 복원을 함께 처리한다.
[상세 기능 요구사항]
1) 취소 가능 여부 판정 후 결제사 취소 API 호출
2) 취소 성공 시 재고 복원 및 주문 상태 변경
[제약 조건]
- 배송 시작 이후 건은 취소 불가
- 결제사 API는 하루 1만 건 한도, 초과 시 지연 처리
- 취소 이력은 삭제하지 않고 보존
[검증 기준]
- 취소 요청 시 결제 취소와 재고 복원이 모두 반영됨
- 시스템이 안정적으로 동작함
	기획팀 홍길동	수용	High	DEV: 김철수	개발중	-
```

**출력**

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
[REQ-F-014] 주문 취소 처리
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

■ 배경
  결제 완료된 주문의 사용자 취소 요청 시, 결제 취소와 재고 복원이
  함께 처리되어야 한다.

■ 작업 범위
  1) 취소 가능 여부 판정
  2) 결제사 취소 API 호출
  3) 재고 복원
  4) 주문 상태 변경

■ 완료 조건
  ✅ 취소 요청 시 결제 취소와 재고 복원이 모두 반영된다
  ✅ 취소 이력이 보존된다 (제약에서 이동 — 달성해야 할 품질)
  ⚠️ (모호) "시스템이 안정적으로 동작함"
     → 대안: "결제사 API 호출 실패 시 재고가 복원되지 않고,
              주문 상태도 변경되지 않는다 (부분 반영 없음)"

■ 제약 (하지 말 것)
  - 배송 시작 이후 건은 취소 불가
  - 취소 이력 삭제 금지

■ 전제
  - 결제사 API 일 1만 건 한도, 초과 시 지연 처리

■ 산출물
  소스 코드 (상태: 개발중)

■ 우선순위 / 분류
  High / 주문 > 결제 > 취소

━━━ 결손 진단 ━━━
⚠️ "안정적으로 동작"은 판정할 수 없습니다. 위 대안이 의도와 맞습니까?
   부분 반영을 어디까지 허용하는지가 핵심입니다.

❓ 취소 가능 여부 판정 기준이 원문에 없습니다.
   배송 시작 외에 취소를 막는 조건이 더 있습니까? (기간 제한, 부분 취소 등)

❓ 결제사 API 호출이 실패하거나 한도를 초과했을 때
   사용자에게 무엇을 보여줍니까?

📌 실명 제거: 요청자·담당자는 '기획 담당 / 개발 담당'으로 처리했습니다.
```

**여기서 일어난 일** — 원문 검증 기준 2개 중 하나는 판정 불가능했고, 제약에 섞인 "이력 보존"은 금지가 아니라 달성 목표라 완료 조건으로 올라갔다. 그리고 실패 처리 시나리오가 통째로 비어 있다는 사실이 착수 전에 드러났다. 이 세 가지는 원문을 그냥 옮겼다면 검수 단계에서야 발견됐을 것들이다.

## 8. 테스트 시나리오

### 정상 흐름
**프롬프트**: "이 요구사항 행을 작업 지시서로 바꿔줘" + 블록 구조가 완비된 엑셀 행
**기대 결과**: 제목이 명사구로 정규화됨 / 완료 조건마다 측정 가능·모호 판정이 붙음 /
제약이 금지·완료 조건·전제로 3분할됨 / 결손 진단 섹션이 함께 나옴

### 결손 흐름 (핵심 검증)
**프롬프트**: 완료 조건 블록이 없는 요구사항 한 줄
**기대 결과**: 완료 조건을 **만들어내지 않는다**. "이 요구사항이 끝났다고 판단할
기준은 무엇입니까"를 확인 질문으로 낸다. 그럴듯한 완료 조건이 생성되면 실패다.

### 엑셀 복붙 흐름
**프롬프트**: 엑셀에서 데이터 행 2개를 선택해 그대로 붙여넣기
(상세 내용 셀의 줄바꿈 때문에 화면상 20줄 이상으로 쪼개져 보임)
**기대 결과**: 줄 수로 행을 세지 않고 식별자 위치로 2건을 인식한다.
판정이 안 되면 "2건으로 보입니다, 맞습니까"를 먼저 확인한다. 20건으로 세면 실패다.

### 범위 밖 흐름
**프롬프트**: "오늘 점심 뭐 먹지?"
**기대 결과**: 억지로 변환하지 않고 스킬 범위와 올바른 입력 형태를 한 줄로 안내한다.

### 시연 흐름 (심사·첫 사용 대비)
**프롬프트**: 스킬만 호출하고 아무 자료도 주지 않음 → 이어서 "샘플로 보여줘"
**기대 결과**: 안내만 하고 끝내지 않고 샘플 시연 경로를 제시한다. "샘플로 보여줘"
요청 시 §7 예시 입력으로 전 과정을 수행해 결과를 내고, 마지막에 "실제 자료를 넣어
보세요"로 닫는다. 안내만 하고 끝나거나, 시연 후 실제 자료 유도가 없으면 실패다.
